## Источники

- Видео: `I:\Мой диск\Vvuzz\2026-04-16 13-15-49.mp4`
- Транскрипт: `I:\Мой диск\AGENTS\Vvuzz\2026-04-16-video-transcribe\2026-04-16 13-15-49.txt`

- Переписка с заказчиком от 05.06.2026, переданная пользователем в чат.

## Факты из видео

- Сервис строится вокруг Госуслуг / "Поступление в вуз онлайн".
- Интересуют бакалавриат, специалитет и базовое высшее.
- Магистратура на первом этапе не нужна.
- Внутри вуза есть программы/направления и конкурсы/квоты.
- У конкурса есть количество мест, включая бюджетные и платные.
- ID абитуриента одинаковый во всех списках.
- По ID нужно находить абитуриента во всех списках.
- Важные признаки:
  - подано согласие;
  - основной приоритет;
  - проходной приоритет;
  - приоритет конкурса.
- Сумма баллов для первого функционала названа менее важной.
- Основной вопрос: сколько людей выше пользователя уже ушли в другие вузы/конкурсы со своими согласиями.

## Факты из переписки

- Заказчик хочет как можно ближе к real-time, но понимает, что это почти нереалистично.
- Задержка 24-48 часов обсуждалась как технически возможная, но для принятия решения она может быть слишком большой.
- В 2025 уже был парсер.
- По словам исполнителя 2025:
  - было около 143 000 запросов;
  - прогресс в одном сообщении был 102 000 / 143 000;
  - получилось 116 077 таблиц, локально в архиве проверено 116 093 `.xlsx`;
  - на сервере Госуслуг был троттлер;
  - больше 60 запросов в минуту на IP давало бан примерно на 3 часа;
  - использовались 4 сервера на разных IP;
  - данных было около 3 ГБ JSON до Excel-представлений.
- Заказчик указывает, что в 2026 вузы обязаны вести учет зачисления через Госуслуги, поэтому данные могут быть чище, чем раньше.
- Проект нужен каждый год, а не как одноразовый ручной сбор.

## Ограничения текущего локального интерфейса

- Интерфейс предназначен для локального анализа, не для публичного production.
- Нет шифрования паролей.
- Нет многопользовательской модели прав.
- Нет live-обновлений.
- Нет парсера Госуслуг 2026.
- Метрики считаются по статическому снимку 2025.

## Технические выводы

- SQLite подходит для локального прототипа и быстрых поисков по ID при наличии индексов.
- Индексы обязательно нужны:
  - `entries(applicant_id)`;
  - `entries(competition_id, ordinal)`;
  - `entries(has_consent, applicant_id)`;
  - индексы по основным полям `competitions`.
- Тяжелые self-join запросы по всей таблице могут быть слишком медленными.
- Для страницы конкурса лучше сначала брать список ID выше пользователя в конкретном конкурсе, затем батчами искать их согласия в других конкурсах.

## Product Risk

Главная ценность сервиса возникает в коротком окне после публикации конкурсных списков. Если обновление данных занимает 24-48 часов, это может быть недостаточно полезно для абитуриента. Более реалистичная продуктовая формулировка: сервис оценки шансов по последнему доступному снимку данных с прозрачным временем обновления.
