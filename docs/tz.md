# ТЗ: локальный сервис анализа списков поступления в вуз

## 1. Цель

Сделать локальный интерфейс для изучения больших публичных данных из списков поступления в вуз онлайн и проверки гипотезы будущего сервиса для абитуриентов.

Ключевой пользовательский вопрос: по ID абитуриента понять, где он найден, на какой позиции находится, сколько людей выше него, и сколько из этих людей уже имеют согласие в этом или других конкурсах.

## 2. Пользовательская ценность

Абитуриенту важно решить, куда подавать единственное согласие. Простого места в списке недостаточно: если выше него много людей уже подали согласия в другие конкурсы, реальный риск ниже, чем кажется по позиции.

Сервис должен превращать множество разрозненных конкурсных списков в понятную картину по одному ID.

## 3. MVP на архиве 2025

Локальный MVP должен:

- импортировать архив `2025-07-24 13-40-58.zip` в SQLite;
- хранить конкурсы и строки абитуриентов в нормализованном виде;
- давать вход по простому логину/паролю из таблицы `users`;
- искать абитуриента по `applicant_id`;
- показывать все конкурсы, где найден ID;
- показывать вуз, программу, тип конкурса, количество мест, позицию, приоритет, согласие и статус;
- открывать страницу конкурса и считать людей выше пользователя;
- давать публичный поиск по `applicant_id` без входа, без переходов по соперникам;
- давать `admin` и `manager` навигацию по вузам, конкурсам, абитуриентам и связям между ними;
- давать `admin` управление пользователями;
- считать среди людей выше:
  - всего людей выше;
  - сколько имеют согласие в этом конкурсе;
  - сколько имеют согласие в других конкурсах;
  - сколько без найденного согласия;
- показывать время/источник загрузки данных через документы и README.

## 4. Не входит в текущий MVP

- полностью автоматический live-discovery Госуслуг 2026 до фиксации актуальных URL/API;
- надежная production-аутентификация;
- шифрование паролей;
- юридическая оценка регулярного сбора данных;
- обход антибот-защиты Госуслуг;
- real-time обновление данных.

## 5. Данные

Источник MVP: `I:\Мой диск\Vvuzz\2025-07-24 13-40-58.zip`.

Архив содержит Excel-файлы `.xlsx`, каждый файл соответствует отдельному конкурсу/квоте. Путь внутри архива несет важные измерения:

- код и название направления;
- уровень образования;
- город;
- вуз;
- форма обучения;
- тип конкурса/квоты;
- количество мест в квадратных скобках.

Основные поля строки:

- порядковый номер;
- ID участника;
- приоритет конкурса;
- подано согласие;
- сумма баллов;
- баллы за ВИ;
- баллы за ИД;
- статус;
- дата выбора конкурсной группы по Москве.

## 7. Интерфейс

Главная страница:

- количество конкурсов;
- количество строк абитуриентов;
- количество пользователей;
- поле поиска по ID участника;
- таблица найденных конкурсов.

Страница конкурса:

- вуз;
- программа;
- тип конкурса;
- число мест;
- позиция выбранного ID;
- метрики по людям выше;
- первые 200 людей выше в списке.

Закрытый аналитический интерфейс для `admin` и `manager`:

- `/universities` - таблица вузов, поиск, счетчики конкурсов/программ/строк;
- `/university?id=...` - конкурсы выбранного вуза;
- `/competitions` - таблица конкурсов с фильтрами;
- `/competition?id=...` - участники конкурса, кликабельные `applicant_id`;
- `/applicants` - поиск и список публичных ID;
- `/applicant?id=...` - карточка участника и все его конкурсы.

Публичный интерфейс:

- `/public` - ввод `applicant_id` без логина;
- `/public/applicant?id=...` - конкурсы, позиции, согласия, статусы и шанс;
- `/public/competition?id=...&focus_applicant_id=...` - обезличенная сверка позиции и метрик без переходов по соперникам.

## 8. Авторизация

Авторизация намеренно простая:

- логины и пароли лежат в SQLite в таблице `users`;
- пароль хранится как обычный текст;
- дефолтный доступ: `prointdata@ya.ru` / `admin`;
- `admin` может создавать, редактировать и деактивировать пользователей через `/admin/users`;
- `manager` видит аналитические таблицы, но не управляет пользователями;
- `applicant` видит привязанный `applicant_id`.

Это соответствует текущей модели: локальный интерфейс для анализа публичных данных, без production security.

## 9. Формула шанса

Формула v1 называется `Balanced` и находится в `chance.py`.

- `above_consent_here` - люди выше с согласием в этом конкурсе, вес `1.0`;
- `above_consent_elsewhere` - люди выше с согласием в другом конкурсе, вес `0.15`;
- `above_no_consent` - люди выше без найденного согласия, вес `0.55`.

```text
effective_blockers = 1.0 * above_consent_here
                   + 0.15 * above_consent_elsewhere
                   + 0.55 * above_no_consent

projected_rank = 1 + effective_blockers
chance_percent = clamp((seats - effective_blockers) / seats * 100, 0, 100)
```

Пороговые значения:

- `>=75%`: высокий шанс;
- `40-74%`: средний шанс;
- `<40%`: низкий шанс.

Обязательный текст рядом с расчетом: "Это эвристическая оценка по текущим публичным данным, не гарантия зачисления".

## 10. Следующий этап после локального MVP

После проверки локального интерфейса на архиве 2025 нужен отдельный технический spike по live-источнику Госуслуг:

1. открыть актуальный сервис поступления;
2. посмотреть сетевые запросы браузера;
3. выяснить, есть ли API/JSON или только HTML/Excel;
4. проверить лимиты и блокировки;
5. понять, можно ли получать изменения чаще полного обхода;
6. оценить стратегию обновления: полный обход, горячие списки, пользовательские приоритеты.

## 11. Главный риск

Функционально сервис простой. Главная сложность - не UI и не SQLite, а надежное, допустимое и достаточно свежее получение данных Госуслуг в короткое окно приемной кампании.
